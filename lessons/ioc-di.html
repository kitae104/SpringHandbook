홈 섹션

IOC_DI Source Reading Class

객체를 누가 만들고, 누가 연결하는가?

이 자료는 IOC_DI 저장소의 실제 소스를 읽으면서 IoC와 DI를 이해하기 위한 강의용 페이지입니다. 목표는 어노테이션 이름을 외우는 것이 아니라, 코드의 제어권과 의존 관계가 어디에서 어디로 이동하는지 보는 것입니다. 같은 주문 기능이라도 객체를 직접 만들 때, 인터페이스로 역할을 분리할 때, Spring 컨테이너에 조립을 맡길 때 코드가 어떻게 달라지는지 비교하면 IoC와 DI가 훨씬 구체적으로 보입니다.

수업 목표
  1. new가 많아질 때 생기는 결합 문제를 찾는다.
  2. 인터페이스와 주입이 어떤 문제를 줄이는지 설명한다.
  3. Spring 컨테이너가 IoC와 DI를 어떻게 실행하는지 연결한다.

Before Reading

이 예제는 자동차 주문 이야기를 빌려 객체 관계를 보여줍니다

예제의 핵심 인물은 TestClient, OrderManager, CarMaker, KiaMaker, HyundaiMaker입니다. TestClient는 프로그램을 실행하는 쪽이고, OrderManager는 판매자 역할을 합니다. 실제 자동차를 만들어 판매하는 쪽은 KiaMaker나 HyundaiMaker입니다. 수업에서는 자동차 자체보다 판매자가 제조사를 어떻게 알게 되는지에 집중하면 됩니다.

1. 객체 생성 위치를 찾기

코드에서 new가 어디에 있는지 먼저 봅니다. 객체를 생성하는 위치는 변경 책임이 놓인 위치입니다.

2. 의존 방향을 확인하기

OrderManager가 구체 클래스에 의존하는지, 인터페이스에 의존하는지 확인합니다. 이 차이가 확장성과 테스트 용이성을 크게 바꿉니다.

3. 변경 지점을 비교하기

제조사를 기아에서 현대로 바꾼다고 가정하고 어느 파일을 수정해야 하는지 비교합니다. 수정 범위가 줄어드는 과정이 설계 개선의 증거입니다.

용어를 먼저 외우지 않아도 됩니다

처음에는 IoC를 "제어권이 이동하는 것", DI를 "필요한 객체를 밖에서 넣어 주는 것" 정도로 잡으면 충분합니다. 이후 코드를 보면서 OrderManager가 직접 만들던 객체를 외부에서 받게 되고, 마지막에는 Spring이 대신 만들고 연결한다는 흐름을 확인하면 두 용어가 자연스럽게 연결됩니다.

Part 1

basic: 판매자가 제조사를 직접 고르는 코드

첫 단계는 Spring을 쓰지 않는 순수 Java 코드입니다. TestClient는 OrderManager만 만들지만, 실제 자동차 제조사는 OrderManager 내부에서 직접 결정됩니다. 이 방식은 입문 단계에서 가장 자연스럽습니다. 필요한 객체가 있으면 그 자리에서 new로 만들면 되기 때문입니다. 다만 코드가 커질수록 "객체를 사용하는 책임"과 "객체를 선택하고 생성하는 책임"이 한 클래스 안에 섞이기 시작합니다.

src/basic/TestClient.java 클라이언트는 판매자만 생성 
OrderManager manager = new OrderManager();
manager.order();
src/basic/OrderManager.java 판매자가 구현체를 직접 생성 
public class OrderManager {
    private KiaMaker maker;

    public OrderManager() {
        maker = new KiaMaker(); // 생성자를 통한 생성 (강결합)
    }

    public void order() {
        Money money = new Money(1000);
        Car car = maker.sell(money);
        System.out.println("판매상 : ((인수)) " + car.getName());
    }
}
문제점

OrderManager는 판매 책임을 가진 클래스인데 KiaMaker라는 구체 제조사까지 알고 있습니다. 제조사를 HyundaiMaker로 바꾸려면 판매자 코드 자체를 수정해야 합니다.

좋은 점

구조가 단순합니다. 작은 예제에서는 객체가 어디서 만들어지는지 바로 보이고, Spring 없이도 실행 흐름을 쉽게 따라갈 수 있습니다.

한계

구현체 교체, 테스트 대역 사용, 확장에 약합니다. 판매자가 자동차 제조사 생성 규칙까지 떠안기 때문에 역할 분리가 흐려집니다.

IoC/DI 관점

아직 IoC도 DI도 거의 없습니다. 객체 생성의 제어권은 OrderManager 안에 있고, 의존 객체도 외부에서 주입받지 않습니다.

basic에서 다음 단계로 넘어가는 이유

지금 코드는 실행만 보면 문제가 없어 보입니다. 하지만 KiaMaker를 HyundaiMaker로 바꾸는 순간 OrderManager를 수정해야 합니다. 판매자는 "자동차를 주문한다"는 유스케이스를 처리해야지, 어느 제조사 클래스를 직접 생성할지까지 책임질 필요는 없습니다. 그래서 다음 단계에서는 판매자가 구체 제조사 이름을 모르게 만들고, 자동차를 판매할 수 있는 공통 역할만 바라보게 합니다.

  • 바뀌어야 하는 것: KiaMaker 직접 의존
  • 유지해야 하는 것: OrderManager.order()의 주문 흐름
  • 새로 필요한 것: 제조사를 대표하는 공통 타입

Part 2

interfaces: 역할에 의존하고 구현체는 밖에서 넣기

두 번째 단계는 CarMaker 인터페이스를 도입합니다. 판매자는 이제 기아나 현대라는 구체 클래스가 아니라 자동차를 판매할 수 있다는 역할에 의존합니다. 여기서 중요한 변화는 "제조사를 바꿀 때 판매자 코드를 고치지 않는다"는 점입니다. OrderManager는 sell()을 호출할 수 있으면 되고, 실제 구현체가 기아인지 현대인지는 외부 조립 코드가 결정합니다.

src/interfaces/CarMaker.java 역할 정의 
public interface CarMaker {
    Car sell(Money money);
}
src/interfaces/OrderManager.java 구현체 대신 인터페이스 의존 
public class OrderManager {
    private CarMaker maker;

    public void setMaker(CarMaker maker) {
        this.maker = maker;
    }

    public void order() {
        Money money = new Money(1000);
        Car car = maker.sell(money);
        System.out.println("판매상 : ((인수)) " + car.getName());
    }
}
src/interfaces/TestClient.java 외부에서 구현체 주입 
OrderManager manager = new OrderManager();

CarMaker maker = new HyundaiMaker();
manager.setMaker(maker); // 주입 하는 방식

manager.order();
해결한 점

OrderManager가 KiaMaker나 HyundaiMaker를 직접 만들지 않습니다. 제조사 변경은 TestClient의 조립 코드에서 처리할 수 있습니다.

장점

판매자는 CarMaker 역할만 알면 됩니다. 새 제조사가 생겨도 CarMaker를 구현하면 같은 판매 흐름에 넣을 수 있습니다.

단점

setter 주입은 setMaker 호출을 빼먹으면 order()에서 문제가 생길 수 있습니다. 또한 객체 생성과 조립 책임은 여전히 개발자가 직접 작성합니다.

IoC/DI 관점

DI의 핵심이 보이기 시작합니다. 필요한 의존 객체를 내부에서 만들지 않고 외부에서 넣습니다. 다만 IoC 컨테이너는 아직 없어서 제어권은 TestClient가 가지고 있습니다.

basic에서 interfaces로 바뀌며 신경 쓸 부분

인터페이스를 만들었다고 자동으로 좋은 설계가 되는 것은 아닙니다. 먼저 공통 역할을 제대로 뽑아야 합니다. 이 예제에서는 KiaMaker와 HyundaiMaker가 모두 돈을 받고 자동차를 판매하므로 CarMaker.sell(Money)이 공통 계약이 됩니다. 반대로 구현체마다 전혀 다른 일을 한다면 억지로 같은 인터페이스에 묶으면 오히려 이해하기 어려운 코드가 됩니다.

  • OrderManager 필드 타입을 구체 클래스에서 CarMaker로 바꿉니다.
  • KiaMaker와 HyundaiMaker는 같은 메서드 계약을 구현합니다.
  • 어떤 구현체를 쓸지는 TestClient가 결정하고 setter로 넘깁니다.
이 단계에서 아직 남아 있는 불편함

의존성을 외부에서 넣는 DI 형태는 만들어졌지만, 조립 책임이 TestClient에 남아 있습니다. 클래스가 3개일 때는 괜찮지만 서비스, 저장소, 설정 객체가 계속 늘어나면 매번 new와 setMaker()를 직접 호출해야 합니다. 또한 setter를 호출하지 않으면 maker가 비어 있는 상태로 실행될 수 있습니다. Spring은 바로 이 "객체 생성과 조립" 문제를 컨테이너가 맡도록 도와줍니다.

Part 3

annotation: Spring 컨테이너가 객체를 만들고 연결하기

세 번째 단계에서는 Spring이 등장합니다. 구현체와 판매자에 어노테이션을 붙이면 ApplicationContext가 객체를 생성하고, 필요한 의존성을 찾아 주입합니다. 이제 개발자는 모든 객체를 손으로 조립하지 않고, 어떤 클래스가 Spring이 관리할 대상인지와 어떤 의존성이 필요한지만 표시합니다. 제어권은 점점 애플리케이션 코드에서 Spring 컨테이너로 이동합니다.

src/annotation/HyundaiMaker.java Bean 후보 등록 
@Component("hyundai")
public class HyundaiMaker implements CarMaker {
    @Override
    public Car sell(Money money) {
        Car car = new Car("쏘나타");
        return car;
    }
}
src/annotation/OrderManager.java 생성자 주입 
@Service
public class OrderManager {
    private CarMaker maker;

    @Autowired
    public OrderManager(@Qualifier("hyundai") CarMaker maker) {
        this.maker = maker;
    }
}
src/annotation/TestClient.java 컨테이너에서 Bean 조회 
ApplicationContext context =
    new ClassPathXmlApplicationContext("car-config-annotation.xml");

OrderManager manager =
    context.getBean("orderManager", OrderManager.class);

manager.order();
수업에서 짚을 부분

이 예제의 annotation 파트는 오래된 Spring 설정 방식 때문에 car-config-annotation.xml로 컴포넌트 스캔을 켭니다. XML 자체를 별도 파트로 다루지 않아도 됩니다. 여기서 핵심은 XML 문법이 아니라, Spring 컨테이너가 @Component와 @Service가 붙은 클래스를 Bean으로 만들고 @Autowired 생성자에 의존 객체를 넣는다는 점입니다.

interfaces에서 annotation으로 넘어가는 이유

interfaces 단계는 설계 방향을 잘 보여 주지만, 객체 조립 코드를 매번 사람이 작성해야 합니다. Spring을 사용하면 조립 코드를 없애는 것이 아니라, 조립 책임을 컨테이너로 옮깁니다. @Component("hyundai")는 "이 클래스를 Spring이 관리하는 객체로 만들어 달라"는 표시이고, @Autowired 생성자는 "이 객체를 만들 때 필요한 의존성을 넣어 달라"는 요청입니다. @Qualifier("hyundai")는 CarMaker 구현체가 여러 개일 때 어느 Bean을 넣을지 명확히 정하는 선택 기준입니다.

  • 직접 생성 코드가 줄어들지만, Bean 후보와 선택 기준은 명확해야 합니다.
  • Spring이 객체를 만들려면 컴포넌트 스캔 범위 안에 클래스가 있어야 합니다.
  • 같은 타입 구현체가 여러 개면 이름, @Qualifier, @Primary 같은 규칙이 필요합니다.
해결한 점

TestClient가 더 이상 OrderManager와 제조사를 직접 조립하지 않습니다. Spring 컨테이너가 Bean을 만들고 의존 관계를 연결합니다.

장점

객체 생성과 연결 규칙이 애플리케이션 시작 시점에 관리됩니다. 여러 클래스가 많아져도 컴포넌트 스캔과 DI 규칙으로 일관되게 조립할 수 있습니다.

단점

연결 과정이 코드 한 줄의 new처럼 직접 보이지 않습니다. 같은 타입 Bean이 여러 개라면 @Qualifier 같은 선택 기준을 명확히 적어야 합니다.

IoC/DI 관점

IoC는 객체 생성과 연결의 제어권이 Spring 컨테이너로 이동한 것입니다. DI는 그 컨테이너가 OrderManager 생성자에 CarMaker 구현체를 넣어 주는 방식입니다.

코드 리뷰 포인트

실제 소스의 OrderManager에는 @Inject가 붙은 필드와 @Autowired 생성자가 함께 있습니다. 수업에서는 두 방식을 모두 보여주는 예제로 설명하되, 정리할 때는 필수 의존성이 명확한 생성자 주입을 권장한다고 알려주는 것이 좋습니다.

처음 보는 학생에게 설명할 때의 핵심 문장

"Spring이 대신 코드를 실행해 준다"라고 설명하면 너무 넓고 모호합니다. 이 예제에서는 "Spring이 HyundaiMaker와 OrderManager 객체를 만들고, OrderManager 생성자에 hyundai Bean을 넣어 준다"라고 구체적으로 말하는 편이 좋습니다. 이렇게 말하면 IoC는 생성과 연결의 제어권 이동, DI는 생성자에 의존 객체가 들어오는 장면으로 분리해서 이해할 수 있습니다.

Wrap Up

세 단계로 정리하는 IoC와 DI

단계 객체 생성 위치 의존 대상 핵심 개념
basic OrderManager 내부 KiaMaker 같은 구체 클래스 강결합, 직접 생성
interfaces TestClient 조립 코드 CarMaker 인터페이스 역할 분리, 수동 DI

학생에게 던질 질문
  • 제조사를 바꾸려면 어느 단계에서 어떤 파일을 수정해야 할까?
  • OrderManager가 꼭 알아야 하는 것은 제조사 이름일까, 자동차를 판매하는 역할일까?
  • Spring을 쓰면 편해지는 부분과 오히려 눈에 덜 보이게 되는 부분은 무엇일까?
핵심 결론

DI는 의존 객체를 밖에서 넣는 설계 방식이고, IoC는 그 객체 생성과 연결의 제어권이 개발자 코드 바깥으로 이동하는 구조입니다. Spring은 ApplicationContext라는 컨테이너로 이 두 개념을 실제 애플리케이션에서 실행합니다. 그래서 Spring 코드를 읽을 때는 단순히 어노테이션을 찾는 데서 멈추지 말고, 이 객체가 Bean으로 등록되는지, 어떤 타입으로 주입되는지, 같은 타입 후보가 여러 개라면 어떤 기준으로 선택되는지를 함께 확인해야 합니다.
