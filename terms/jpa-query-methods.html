홈 수업 핵심 용어 JPA 쿼리 메소드

Spring Data JPA

JPA 쿼리 메소드

Repository 메소드 이름, @Query, Pageable 등을 이용해 조회 조건과 반환 형태를 선언하는 Spring Data JPA 기능입니다.

용어 핵심 약 12분

정확한 뜻

쿼리 메소드는 정확히는 JPA 표준 자체가 아니라 Spring Data JPA가 제공하는 Repository 기능입니다. findByTitleContaining처럼 정해진 이름 규칙을 분석해 JPQL과 SQL을 생성합니다.

Repository 인터페이스는 구현 클래스가 없습니다. 애플리케이션이 뜰 때 Spring Data JPA가 인터페이스를 읽고 프록시 구현체를 대신 만들어 Bean으로 등록하기 때문에, 개발자는 메소드 시그니처만 선언하면 됩니다.

간단한 고정 조건은 메소드 이름으로 표현하고, 이름이 지나치게 길거나 조인·집계가 필요하면 @Query, Specification, QueryDSL 또는 별도 Repository 구현을 선택합니다.

실제로 동작하는 순서

01 메소드 분석

Subject(find, exists, count, delete)와 By 뒤의 Predicate 조건을 파싱합니다.

02 속성 경로 확인

Entity 메타데이터에서 필드와 연관관계 경로가 유효한지 애플리케이션 시작 시점에 검사합니다.

03 쿼리 실행

파라미터를 바인딩하고 반환 타입에 맞게 단건, 목록, Slice 또는 Page 결과를 만듭니다.

04 SQL 확인

Hibernate가 생성한 실제 SQL과 실행 계획을 확인해 성능을 검증합니다.

메소드 이름은 시작 시점에 검증됩니다

오타가 있거나 존재하지 않는 필드를 가리키면 실행할 때가 아니라 애플리케이션이 부팅될 때 PropertyReferenceException이 발생합니다. 배포 전에 바로 오류를 잡을 수 있다는 점이 이름 기반 쿼리의 장점입니다.

Subject 키워드로 동작 종류 정하기

메소드 이름은 By 앞부분(Subject)으로 어떤 동작을 할지, By 뒷부분(Predicate)으로 어떤 조건을 쓸지 나뉩니다. 먼저 자주 쓰는 Subject 키워드를 익혀두면 반환 타입을 예측하기 쉽습니다.

키워드 예시 설명
find…By / read…By / get…By / query…By findByTitle 조회 결과를 List, Optional, Stream, Page, Slice 등으로 반환합니다.
exists…By existsBySlug 조건에 맞는 데이터가 있는지 boolean으로만 확인합니다.
count…By countByPublishedTrue 조건에 맞는 건수를 long으로 반환합니다.
delete…By / remove…By deleteByPublishedFalse 삭제된 건수(long) 또는 void를 반환합니다. 대량 삭제는 벌크 쿼리 사용도 검토합니다.
…First<n>… / …Top<n>… findTop3ByOrderByCreatedAtDesc 결과 개수를 제한합니다. 순서를 보장하려면 OrderBy를 꼭 함께 씁니다.
Distinct findDistinctByTitle 중복을 제거한 결과만 조회합니다.

Predicate 키워드로 조건 표현하기

By 뒤에 오는 필드 이름 사이에 아래 키워드를 조합해 조건을 만듭니다. 여러 키워드를 And / Or로 이어 붙일 수 있지만, 너무 길어지면 가독성이 떨어지므로 이 표만큼만 익혀도 실무 조회의 대부분을 다룰 수 있습니다.

키워드 예시 메소드 생성되는 조건(JPQL)
And findByTitleAndPublished where x.title = ?1 and x.published = ?2
Or findByTitleOrSlug where x.title = ?1 or x.slug = ?2
Is, Equals(생략 가능) findBySlug where x.slug = ?1
Between findByPriceBetween where x.price between ?1 and ?2
LessThan / LessThanEqual findByPriceLessThan where x.price < ?1
GreaterThan / GreaterThanEqual findByPriceGreaterThanEqual where x.price >= ?1
After / Before findByCreatedAtAfter where x.createdAt > ?1
IsNull, Null / IsNotNull, NotNull findByDeletedAtIsNull where x.deletedAt is null
Like / NotLike findByTitleLike where x.title like ?1(직접 %를 붙여야 함)
StartingWith / EndingWith / Containing findByTitleContaining where x.title like ?1(양쪽에 %를 자동으로 붙임)
Not findByStatusNot where x.status <> ?1
In / NotIn findByStatusIn(Collection<Status> s) where x.status in ?1
True / False findByPublishedTrue where x.published = true
IgnoreCase findByTitleIgnoreCase where upper(x.title) = upper(?1)
OrderBy findByPublishedOrderByCreatedAtDesc where x.published = ?1 order by x.createdAt desc

중첩 프로퍼티 경로와 밑줄(_) 표기

연관된 Entity의 필드도 이름만으로 조회할 수 있습니다. Course가 Teacher teacher 필드를 가지고 Teacher에 String name이 있다면, findByTeacherName은 Course에서 곧바로 "teacherName"이라는 필드를 찾다가 없으면 카멜 케이스 경계를 기준으로 teacher.name 경로로 다시 나눠 해석합니다.

// Course.teacher.name 경로를 자동으로 탐색합니다.
List<Course> findByTeacherName(String name);

// Course에 teacherName 이라는 필드가 실제로 존재해 경로가 애매해지면
// 밑줄(_)로 어디까지가 필드이고 어디부터 하위 경로인지 직접 지정합니다.
List<Course> findByTeacher_Name(String name);
초보자가 헷갈리기 쉬운 지점

경로가 여러 단계로 이어지면(teacher.department.name처럼) 카멜 케이스만으로는 Spring Data가 어디서 끊어야 할지 알기 어렵습니다. 조건이 두 단계 이상 중첩되면 처음부터 밑줄로 경계를 명시하는 편이 안전합니다.

반환 타입별로 달라지는 동작

같은 조건이라도 메소드가 어떤 타입을 반환하느냐에 따라 실행되는 쿼리와 처리 방식이 달라집니다.

반환 타입 쓰는 상황 주의할 점
List<T> 0개 이상 결과가 예상될 때 결과가 없으면 null이 아니라 빈 리스트를 반환합니다.
Optional<T> 0개 또는 1개 결과가 예상될 때 실제로 2건 이상 매칭되면 IncorrectResultSizeDataAccessException이 발생합니다.
Stream<T> 대량 데이터를 지연 처리(streaming)할 때 try-with-resources 등으로 반드시 close()해야 커넥션이 반환됩니다.
Slice<T> Pageable과 함께, 다음 페이지 존재 여부만 필요할 때 count 쿼리를 추가로 실행하지 않아 무한 스크롤에 유리합니다.
Page<T> Pageable과 함께, 전체 개수와 총 페이지 수가 필요할 때 count 쿼리가 추가로 실행되어 조건이 복잡할수록 비용이 커집니다.
boolean / long / void exists…By, count…By, delete…By 전용 Subject 키워드에 맞는 타입을 선언해야 컴파일과 파싱이 정상 동작합니다.

비슷한 용어와 구분하기

Derived Query

findByStatusAndTitleContaining처럼 이름으로 조건을 만듭니다.

@Query

JPQL 또는 native SQL을 직접 선언해 복잡한 조회를 명확히 표현합니다.

Page

전체 개수를 위한 count 쿼리를 추가 실행합니다.

Slice

다음 페이지 존재 여부만 확인해 count 쿼리를 피할 수 있습니다.

Optional<T>

0개 또는 1개가 예상되는 단건 결과에 사용합니다.

List<T>

0개 이상 결과를 반환하며 결과가 없으면 빈 목록입니다.

Pageable

page, size, sort 정보를 담아 메소드 파라미터로 전달하는 특수 객체로, 조건 개수에 포함되지 않습니다.

Sort

정렬 조건만 담아 전달하는 특수 파라미터로, OrderBy 키워드 대신 동적으로 정렬을 바꿀 때 사용합니다.

이름 기반 조회와 페이징 예제

public interface CourseRepository extends JpaRepository<Course, Long> {
    Optional<Course> findBySlug(String slug);

    List<Course> findTop10ByPublishedTrueOrderByCreatedAtDesc();

    Slice<Course> findByTitleContainingIgnoreCase(
        String keyword,
        Pageable pageable
    );

    boolean existsBySlug(String slug);

    long countByPublishedTrue();

    List<Course> findByPriceBetween(int minPrice, int maxPrice);

    long deleteByPublishedFalseAndCreatedAtBefore(LocalDateTime cutoff);
}

수업에서 확인할 포인트

  • Entity 필드명이 바뀌면 메소드 이름도 함께 수정해야 하며 잘못된 경로는 시작 시 오류가 날 수 있습니다.
  • And와 Or를 섞은 긴 이름은 우선순위가 읽기 어려우므로 @Query나 다른 조회 도구를 검토합니다.
  • 연관관계 조건은 암시적 join과 N+1을 만들 수 있으므로 실제 SQL을 확인합니다.
  • deleteBy 메소드는 영향 범위와 트랜잭션을 확인하고, 대량 작업은 벌크 쿼리를 별도로 고려합니다.
  • Page가 생성하는 count 쿼리가 복잡한 조회에서 병목이 되지 않는지 확인합니다.
  • Top/First로 개수를 제한할 때 OrderBy 없이 쓰면 어떤 행이 반환될지 DB가 보장하지 않으므로 반드시 정렬 조건을 함께 씁니다.
초보자가 자주 만나는 오류

PropertyReferenceException은 대부분 필드 이름 오타이거나, getter만 있고 실제 필드가 없는 경우, 또는 중첩 경로에서 밑줄 표기가 필요한데 빠뜨린 경우입니다. 메시지에 나오는 필드 이름과 Entity 클래스를 나란히 두고 확인하면 대부분 바로 해결됩니다.

함께 읽을 주제

Repository와 QuerySpring Data JPA의 CRUD, Query Method, JPQL, Native Query, @Query, Pageable, Sort, Specification, QueryDSL 사용 기준입니다.Repository도메인 객체를 조회하고 저장하는 데이터 접근 계층이며, JPA에서는 인터페이스만으로 기본 쿼리를 만들 수 있습니다.JPA자바 객체와 관계형 DB 테이블을 매핑하고 영속성 컨텍스트를 통해 변경 감지, 지연 로딩, 트랜잭션 동작을 제공합니다.Pagination많은 데이터를 한 번에 반환하지 않고 페이지 단위로 나눠 조회하는 API 설계 방식입니다.
